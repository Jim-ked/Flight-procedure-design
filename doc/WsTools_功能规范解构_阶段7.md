# WsTools 功能—规范—算法解构（阶段7）

范围：A2、A3 与 A7/A8/A9/A10 的 CAD 施工几何复用方式；障碍物点、XData、块属性；A10 再校正。

## 1. 本阶段结论

继续核对帮助 HTML、窗口截图、config.xml、Sample 文件以及 DLL 可见 CAD API 名称后，可以把旧 WsTools 的数据传递方式再收紧一层。

目前最符合证据的架构不是“模块间传递完整程序对象”，而是两套并行机制：

### 机制 A：程序施工几何通过坐标复用

用于：
- DER / THR
- FAF / FAP 类基准位置
- SOC
- TP
- KK′
- C
- IF
- IAF方向
- 航段起终点

其典型交互是：

`前序功能计算并绘图`
→ `图面留下施工点/线`
→ `下游窗口通过小型拾取按钮重新拾取坐标`
→ `只把 X/Y/Z 或距离带入窗口`
→ `继续计算`

### 机制 B：障碍物通过 CAD 实体复用

用于：
- 障碍物点批量载入
- 名称
- 高度
- 树高
- 总高度
- 标记
- 行点击后高亮/居中

其典型交互是：

`屏幕数据`
→ `选择/读取点实体`
→ `提取实体附加业务信息`
→ `障碍物列表`
→ `一键评估`

这两种机制在帮助文字和 UI 上有明显区别。

## 2. “拾取点”与“屏幕数据”不是同一种操作

### 2.1 A7 的区别最明显

A7 帮助写法：

TP / KK′ / C 旁边的小按钮：
- 在跑道延长线上拾取 TP 点；
- 拾取定位容差最早点 KK′；
- 拾取最晚点 C；
- 自动换算相对 TP 或 DER 的距离。

而“屏幕数据”按钮：
- 拾取当前屏幕中的所有点实体；
- 读取名称、坐标、高度；
- 填入障碍物列表。

这说明至少在业务接口上，两者不是同一类数据。

TP/KK′/C 的下游结果只有：
- 数值距离；
- 坐标位置。

没有：
- 实体名称；
- ID；
- 业务类型；
- XData 字段。

因此 A7 很可能只消费点坐标。

### 2.2 A8 的 UI 结构相同

A8 中：

KK′左侧边界、右侧边界各有自己的小型拾取按钮。

窗口另一侧又有独立的大按钮：
- 屏幕数据；
- 一键评估；
- 标记。

这再次说明：

`KK′端点拾取`
与
`障碍物实体读取`

属于不同交互通道。

### 2.3 A10 更清楚

A10 的“导航台位置”“IF位置”“IAF方向”三个分组，各自都有单独的小型拾取按钮。

窗口下方另有独立的“屏幕数据”按钮和障碍物列表。

所以 A10 需要的程序几何输入很可能只是三个坐标：

`Navaid Point`
`IF Point`
`IAF Direction Point`

而障碍物才是从 CAD 实体中批量读取。

这进一步降低了“A10自动读取一个既有 FAF/IF 语义对象”的可能性。

## 3. A2 的六个页签实际上是一套“施工距离生成器”

继续查看六张界面示意图后，A2 的内部逻辑比帮助文字更清楚。

### 3.1 FAF 计算

输入：
- IF—FAF 中间段长度；
- FAF高度；
- THR标高；
- GP；
- RDH。

计算：

`FAF-THR = (H_FAF - H_THR - H_RDH) / tan(GP)`

CAD 按钮要求：
- 拾取位置基准；
- 指定方向；
- 绘制 IF、FAF、THR 相关施工位置。

这里的“FAF”名称不能直接等同于所有规范场景中的 FAF。对于精密/APV场景，它可能实际上承担 FAP 或 FAP 上下降定位点的施工功能。

### 3.2 非精密 SOC

这一页的示意图非常关键。

图中明确把 MAPt 到 SOC 的 18 s 拆成：

- 3 s：MAPt 后反应距离 `d`
- 15 s：过渡距离 `X`

也就是：

`总距离 = 3 s + 15 s`

这与此前规范分析吻合。

因此帮助表格把“18 s”写成一个总计时只是 UI 简化；旧程序在业务思想上知道 3 s 与 15 s 是两个不同阶段。

代码逆向时必须确认：
- 是否内部真的分别计算 3 和 15；
- 还是只把两者在 UI/示意图中区分，数值代码仍直接乘 18。

### 3.3 精密 SOC

示意图明确展示：

`SOC = (DH - HL) / tan(GP) + Xz`

并以 THR 为基准绘制 SOC。

这表明精密 SOC 是“沿跑道/复飞方向的一维施工位置”。

### 3.4 复飞 TP

由：
- SOC高度；
- 转弯高度；
- 复飞梯度；

生成 SOC 至 TP 的距离。

CAD 中再从 SOC 沿复飞方向放置 TP。

### 3.5 离场 TP

由：
- DER高度；
- 转弯高度；
- PDG；

生成 DER 至 TP 距离：

`(H_TP - H_DER - 5) / PDG`

再从 DER 沿离场方向放置 TP。

### 3.6 C 容差

示意图直接给出：

`C = (TAS + 56) × (3 + 3) / 3.6`

其中：
- 3 s：飞行员反应时间；
- 3 s：建立坡度时间；
- 56 km/h：最不利顺风。

因此 C 页不是泛化的“6秒距离”，而是明确服务于转弯最晚位置构造。

CAD 操作：
- 拾取转弯最晚点；
- 拾取飞行方向；
- 放置 C 容差线。

## 4. A2 → A3 → A7 的指定点离场施工链现在更可信

可以形成如下候选操作过程：

### 第一步：建立跑道基准

`RCL`
→ 拾取 THR / DER
→ 生成跑道中线及延长线。

### 第二步：建立理论 TP

`A2 离场TP`
→ DER + PDG + 转弯高度
→ 计算 TP 距离
→ 在跑道延长线上画出 TP。

### 第三步：建立定位容差

`A3 定位容差`
→ 使用导航设施类型、精度、DME距离、航迹线等
→ 画定位容差区
→ 可画 KK 线 / 航迹容差。

这里得到的 KK′/最早边界是程序规定的定位误差，而不是 A7 内部凭空产生。

### 第四步：建立最晚技术容差

`A2 C容差`
→ 从已有转弯最晚位置
→ 沿飞行方向放置 6 s 技术容差 C。

### 第五步：A7 只提取三个纵向关系

A7 定点转弯的小按钮重新拾取：

- TP；
- KK′；
- C。

然后把它们转换为：
- TP—DER；
- KK′—TP；
- C—TP。

A7 不一定需要知道这些 CAD 实体“叫什么”，只需要坐标在跑道轴向上的相对位置。

这能够解释 A7 为什么把“最早TP”和“最晚TP”设计成不可直接输入，只能由拾取按钮更新。

## 5. A7 很可能并不消费 A2/A3 的 XData

帮助和 UI 都倾向于这一判断。

如果 A7 真正读取语义对象，典型交互应更像：
- 选择 TP 实体；
- 选择 KK′线；
- 选择 C 实体；
- 软件识别其类型并读取属性。

但帮助始终写：
- “在跑道延长线上拾取 TP 点”
- “拾取 KK′”
- “拾取 C”
- “自动计算对应距离”

而没有：
- 选择实体；
- 识别对象；
- 读取属性。

所以当前最高概率是：

**A7 使用 GetPoint 类坐标交互，而不是读取上游施工对象的 XData。**

这需要 Codex 以后用 API 调用直接证明。

## 6. A10 中 FAF 的问题进一步收敛

阶段5曾错误地把效果图中的 FAF 直接归因于 A10。

阶段6已经撤回。

阶段7进一步确认：

A10 UI 只需要：
- 导航台位置；
- IF位置；
- IAF方向。

这三个输入都有独立坐标拾取按钮。

因此 A10 的核心几何完全可以由三点定义：

1. 导航台 O；
2. IF；
3. IAF 方向参考点。

由 `O→IF` 得到 DME 弧半径；
由 `O→IAF方向点` 得到起始径向；
由 IF 决定弧终止方位。

所以 A10 并不需要 FAF 才能完成其核心 DME 弧任务。

效果图中的 FAF 更可能是：
- 预先由 A2/其他工具画出的背景施工点；
- 或完整教学示例图中的上下文对象。

下一步代码验证只需要看 A10 CAD 方法的 `AppendEntity` 集合中有没有 FAF 标记/文字。

如果没有，则可以正式排除“A10自动生成FAF”。

## 7. 障碍物的数据结构比程序施工点更可能使用 XData

### 7.1 帮助明确称“点实体”

A7 的“屏幕数据”说明非常具体：

`拾取当前屏幕中的所有点实体（障碍物），读取名称、坐标、高度`

而 RandomPoint 明确生成：
- 随机点；
- 名称；
- 高度；
- 可显示文字。

问题在于：

普通 AutoCAD DBPoint 本身并没有“名称、树高、障碍物高”这样的业务字段。

因此这些业务数据必须存放在其他地方。

可能机制包括：
1. XData；
2. ExtensionDictionary；
3. 与 DBText/MText 的空间关联；
4. BlockReference + Attribute；
5. 自定义对象。

结合 DLL 中存在：
- get_XData
- set_XData
- GetXDataForApplication
- ResultBuffer
- RegAppTable

以及公开的 `xInfo` 命令，

**XData 是目前最强的候选。**

但仍需代码证明。

### 7.2 “标记”输出与源障碍物可能不是同一种实体

A7 帮助明确说：

`标记`会把选中障碍物“以图块形式标记到图中（含高度属性）”。

因此应区分：

源障碍物：
- 可能是 DBPoint + XData；

评价后的标记：
- 很可能是 BlockReference + AttributeReference。

不要在逆向时把两者混为一个数据模型。

### 7.3 A10 截图进一步暴露障碍物字段

A10 障碍物表包含：
- ID；
- 名称；
- 高度；
- 树高；
- 总高度；
- 所属区域；
- MOC；
- OCA。

这至少说明“屏幕数据”导入后，内部障碍物对象不是简单的 XYZ 点，而是带多个业务属性的数据结构。

应优先恢复这个内部 Obstacle 类/结构。

## 8. XData 的逆向优先顺序应该调整

不要先从保护区 Polyline 的 XData 入手。

应先打通最容易验证的一条链：

`Y92_RandomPoint`
→ 随机障碍物点
→ set_XData ?
→ xInfo
→ GetXDataForApplication ?
→ A7/A8/A9/A10/B3/B4 的“屏幕数据”
→ 障碍物对象
→ 列表字段。

这一条链有明确的输入、实体和输出，最容易判断 XData schema。

一旦恢复 schema，再检查：
- FAF；
- TP；
- KK′；
- C；
- 保护区；

是否也写入同一或其他 RegApp 数据。

## 9. config.xml 进一步支持“模块之间不共享完整状态”

config.xml 能保存大量窗口控件状态，例如：
- A7 的 TP—DER；
- KK′—TP；
- C—TP；
- turn end X/Y；
- 各类 IAS、风、坡度。

但没有看到一个统一的：
- Procedure；
- Fix list；
- Segment list；
- Entity Handle map；
- FAF/TP/KK/C 对象引用。

配置文件的结构仍然是：

`FormName → ControlName → Value`

这进一步说明旧软件持久化的是 UI 状态，而不是完整的程序业务模型。

目前后者没有证据。

→ XData/实体

### 第二小组：施工坐标链

`A2 CAD`
→ `A3 CAD`

## 13. 对后续自动设计系统的直接启示

旧软件中的“人工重新拾取”可以分成两类。

### 规范本身要求设计人员决策

例如：
- 选择程序类型；
- 选择导航设施；
- 选择转弯方式；
- 确定程序高度；
- 判断某些非标准情况是否允许。

这类不能简单删除。

### 旧软件缺乏统一数据模型导致的重复拾取

例如：
- 已计算 TP 后 A7 再点一次 TP；
- 已绘 KK′ 后再次点 KK′；
- 已有 IF 后 A10 再输入 IF；
- 已有保护区边界后 A6 再手工选 Polyline 做包络。

这类在新系统中原则上应由对象引用自动完成。

所以当前逆向不只是恢复公式，还要给每个人工动作加一个属性：

`RegulatoryDecision`
或
`LegacyUIWorkaround`

后续自动化设计时，只有第二类应优先消除。
