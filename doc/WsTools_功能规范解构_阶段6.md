# WsTools 功能—规范—算法解构（阶段6）

范围：基础功能复用方式、A10 修正、CAD 图面作为共享工作区、XData 使用边界、后续逆向策略。

## 1. 对阶段5中 A10 的修正

阶段5曾提出：A10 效果图中出现 FAF，而帮助页没有 FAF 输入，因此 FAF 可能由 A10 内部自动生成。

继续核对 `FormCalcu.html`、`FormDmeEvl.html`、`FormDepartureEvl.html`、`FormTurnAreaEvl.html` 和效果图后，应当修正这一判断。

A2“飞行程序基础计算”明确不是只显示数值的计算器。六个选项卡均支持 CAD 绘制：

- FAF 计算：计算 IF—FAF 中间段和 FAF—THR 距离，CAD 中按基准点和方向绘制；
- 非精密 SOC：从 MAPt 定位容差最晚点沿复飞方向绘制 SOC；
- 精密 SOC：从 THR 沿复飞方向绘制 SOC；
- 复飞 TP：从 SOC 沿复飞方向绘制 TP；
- 离场 TP：从 DER 沿离场方向绘制 TP；
- C 容差：从转弯最晚点沿飞行方向绘制 C 容差线。

因此，A10 示例图中的 FAF 完全可能是由 A2 或前序作图步骤预先构造的背景几何，而不是 A10 自身产生。

A10 帮助对其自身能力的描述始终限定为：

- 输入导航台；
- 输入 IF；
- 输入 IAF 方向；
- 评估 DME 弧；
- 绘制 DME 弧保护区；
- 对障碍物进行评价。

没有任何文字说明 A10 会计算或生成 FAF。

所以当前更稳妥的结论是：

**A10 效果图是一个组合设计场景截图，不能把图中所有对象都归因于 A10。**

这也说明后续分析必须严格区分：
1. 当前命令新生成的对象；
2. 当前命令读取/拾取的已有对象；
3. 示例图中为了说明上下文而预先存在的对象。

## 2. WsTools 很可能采用“CAD 图面复用”，而不是“模块数据模型复用”

继续核对帮助文件后，旧软件的工作方式已经表现出明显规律。

### 2.1 A2 负责先构造基础点和施工线

A2 可以在 CAD 中放置：
- FAF；
- SOC；
- 复飞 TP；
- 离场 TP；
- C 容差线。

它们本身是后续程序设计的基础几何条件。

### 2.2 A3 负责构造定位容差和 KK′ 类限制

A3 可绘制：
- 定位容差区；
- 航迹线；
- KK 线；
- 航迹容差。

这些几何对象直接服务于指定点转弯、复飞转弯、传统程序衔接。

### 2.3 下游模块再次从图面拾取

A7 定点转弯明确要求设计人员在跑道延长线上重新拾取：
- TP；
- KK′；
- C。

软件只把拾取坐标换算成：
- TP—DER；
- KK′—TP；
- C—TP。

A8 同样要求输入/拾取 KK′线左右端点。

A10 要求输入/拾取导航台、IF 和 IAF 方向。

A9 要求输入/拾取航段起终点。

这些交互共同说明：

**各功能之间的主要共享介质很可能就是 CAD 图纸本身。**

也就是说，典型操作链更像：

`基础工具画施工点/线`
→ `设计人员目视确认`
→ `下游功能重新拾取这些几何`
→ `软件计算距离/角度`
→ `继续画保护区`

而不是：

`A2 创建 FAF DomainObject`
→ `A10 从统一 Procedure Model 自动取得 FAF`

这一区别非常重要。

## 3. 当前可以形成的传统程序“施工链”

### 3.1 指定点离场

较合理的旧软件工作流是：

`RCL`
→ 建立跑道中线/延长线

`A2 离场TP`
→ 从 DER 沿离场方向放置理论 TP

`A3 定位容差`
→ 在 TP 附近形成最早/最晚定位限制，得到 KK′ 等辅助线

`A2 C容差`
→ 从相关最晚位置沿航迹方向放出 6 s 飞行技术容差 C

`A7 定点离场`
→ 重新拾取 TP / KK′ / C
→ 计算三者相对 DER/TP 的距离
→ 构造转弯起始区、转弯区
→ 障碍物评价

这比让 A7 自己从零计算 TP、KK′、C 更符合帮助中实际暴露的交互。

### 3.2 指定高度离场

`RCL`
→ 跑道中线

`A2 离场TP`
→ 可先按转弯高和 PDG 构造 TP/K-K 位置

`A7 定高离场`
→ 使用转弯高度/PDG重新计算或确认 K-K 距离
→ 构造保护区

这里需要代码确认 A7 是否完全自行重算，还是仍可利用图上已构造点。

### 3.3 复飞转弯

`A2 非精密SOC` 或 `A2 精密SOC`
→ 构造 SOC

`A2 复飞TP`
→ 构造理论 TP

`A3 定位容差`
→ 构造指定点转弯的 KK′/最早限制

`A2 C容差`
→ 构造最晚转弯技术容差

`A8`
→ 输入 KK′左右端点、Ds、PDG、MOC等
→ 做转弯区障碍物评价

因此 A8 没有绘制按钮是合理的：它可能假定保护区关键几何已经通过前序工具构造完成，自己主要负责评价。

## 4. A10 的正确理解应改成“在既有进近结构上补 DME 弧”

结合帮助页和效果图，更合理的使用场景是：

1. 先由其他基础工具建立后续直线进近结构；
2. IF 已经存在；
3. FAF 可能已由 A2 或其他程序构造；
4. A10 只需要导航台、IF 和 IAF 方向；
5. A10 以导航台为圆心、以既定 DME 半径和 IAF 方位构造弧段保护区；
6. 在 IF 处与已有的后续进近结构相接；
7. A10 对其负责的弧段/衔接区障碍物进行评价。

因此阶段5中“FAF必须由A10内部自动生成”的待逆向问题应删除。

新的代码问题应变成：

- A10 在绘图前是否读取已有 IF/FAF 实体，还是仅使用用户拾取的 IF 坐标；
- A10 是否只生成 DME 弧部分，IF 后的直线区只是示例图背景；
- A10 的障碍物评价范围是否截止于 IF；
- 如果评价范围跨过 IF，后续直线保护区几何来自 A10 内部重建，还是来自已有 CAD 边界。

## 5. A2 FAF 还需要注意“FAF/FAP术语简化”

A2 的 FAF 公式为：

`FAF-THR = (FAF高度 - RDH - THR标高) / tan(GP)`

这是沿给定垂直航径由高度反求水平距离的计算。

从严格规范术语看，这种几何关系更接近：
- 精密进近的 FAP；
- Baro-VNAV 的 FAP；
- 或在 FAP 设置下降定位点后形成的 FAF。

旧软件界面统一称“FAF计算”，很可能属于作者为了教学/作图方便所作的术语简化。

所以逆向代码时不应仅凭字段名 `FAF` 判断程序类型，应结合：
- GP/VPA；
- RDH；
- 中间段；
- OAS/APV模块中的调用关系；
来判断其真实业务用途。

## 6. XData：目前不能证明基础几何是“语义对象”

DLL 中可见：
- `get_XData`
- `set_XData`
- `GetXDataForApplication`
- `ResultBuffer`
- `RegAppTable`

帮助中还公开了命令：

`xInfo`

用于选择实体并把 XData 以 JSON 层级输出。

这说明 WsTools 确实在使用 AutoCAD XData。

但是目前没有证据证明：
- A2 生成的 FAF；
- A2 生成的 TP；
- A2 生成的 C 容差线；
- A3 生成的 KK′线；

一定都带有可供其他模块自动识别的语义 XData。

相反，下游窗口反复要求用户重新拾取几何位置，这更支持“几何复用”而不是“语义对象自动复用”。

因此暂时分成两种可能：

A. 施工几何仅是普通 Line/Point/Text，模块靠人工拾取复用；  
B. 施工几何同时带 XData，但旧界面仍要求人工选择，XData用于检查、标记或其他辅助功能。

后续代码逆向必须专门验证这一点。

## 7. XData 最值得先查的对象不是保护区，而是障碍物点

多个评价窗口的“屏幕数据”功能会：

- 拾取屏幕中的点实体；
- 读取名称；
- 读取坐标；
- 读取高度；
- 填入障碍物列表。

随机点工具生成的点又可以直接用于后续越障评估。

因此 XData 最可能首先承担的是“障碍物点属性”保存，例如：
- ID；
- 名称；
- 高度；
- 树高；
- 总高；
- 经纬度/平面坐标。

这比直接假定所有程序施工线均带业务 XData 更符合当前证据。

所以后续对 `set_XData / GetXDataForApplication` 的调用追踪，应优先建立：

`随机点/障碍物导入`
→ `Point/Block实体`
→ `XData JSON`
→ `屏幕数据`
→ `障碍物列表`

如果这一链能恢复，再检查施工点/保护区是否复用同一机制。

## 8. 无窗口命令进一步支持“CAD施工工具箱”架构

帮助中心列出：

- `RCL`：跑道中心延长线，两端延长40 km；
- `NMCIRCLE`：以海里为单位连续画圆；
- `rectLine`：按起终点和宽度画矩形；
- `Arc2`：以圆心和弧上点画左右30°圆弧；
- `xInfo`：检查 XData。

这些命令没有完整程序业务上下文，都是典型的施工几何工具。

C3 `exline` 也是：
- 输入扩张角；
- 输入长度；
- 拾取起点；
- 生成外扩边界。

A6 的“包络线”甚至明确要求：
- 设计人员先分别画好多条模板；
- 再手工选择已绘制的多段线；
- 软件合并成包络。

所以旧 WsTools 的总体架构现在可以更准确地概括为：

**以 AutoCAD 图面为状态空间、以规范计算器和几何命令为工具、由设计人员组织设计顺序的半自动飞行程序设计工具箱。**

这比把它理解成一个内部拥有完整 Procedure 数据模型的自动设计软件更符合现有证据。

## 9. 后续逆向重点因此需要调整

### 不应优先追求

- 恢复所有 Form 之间的数据传递；
- 寻找一个可能不存在的完整程序对象模型；
- 假设每个窗口会自动取得前序模块结果。

### 应优先恢复

1. 每个基础功能到底画了哪些实体；
2. 每个实体的几何定义；
3. 绘制时要求用户提供哪些基准点和方向；
4. 下游功能要求重新拾取哪些点；
5. 拾取后如何转化为距离、角度、保护区参数；
6. 是否存在 XData，以及 XData 的真实用途；
7. 哪些计算在多个窗口中重复实现；
8. 哪些几何函数是共用底层库。

## 10. 下一批最有价值的代码验证问题

### A2

1. FAF页 CAD 按钮到底创建哪些实体：THR、FAF、IF、垂线、文字、中心线分别有哪些。
2. FAF页拾取的“位置点”在业务上究竟是 THR、FAF 还是其他基准点。
3. 离场TP、复飞TP、SOC、C容差的 CAD 输出分别是 Point、Line、Polyline、DBText 还是组合。
4. 这些实体是否写 XData。
5. 如果有 XData，注册应用名和 JSON 结构是什么。

### A3

6. KK线、航迹线、定位容差区分别是什么实体。
7. 是否写入“fix/kk/tolerance”等语义 XData。
8. 下游模块是否直接读取 A3 的实体，还是只读取拾取的坐标。

### A7

9. TP/KK′/C 图标按钮使用的是 `Editor.GetPoint` 还是 `GetEntity`。
10. 如果是 GetPoint，基本可确认 A7 只消费坐标，不消费上游语义对象。
11. 如果是 GetEntity，则继续查是否读取 XData/几何交点。

### A10

12. CAD 按钮新增实体集合与命令前后差异。
13. FAF 是否属于 A10 新增实体。
14. 一键评价的几何范围是否跨过 IF。
15. IF 后的直线区如果参与评价，几何从哪里取得。

### XData

16. `set_XData` 的调用者优先按 RandomPoint、障碍物导入、标记功能分类。
17. `GetXDataForApplication` 的调用者是否集中在“屏幕数据”功能。
18. 只有确认施工几何也使用 XData 后，才建立跨模块语义复用模型。

## 11. 对后续新系统的意义

旧 WsTools 的人工拾取并不意味着这些步骤本质上不可自动化。

恰恰相反，很多人工拾取是因为旧软件没有维护完整的程序拓扑关系。

例如：
- A7 让人重新点 TP/KK′/C；
- A8 让人重新点 KK′左右端；
- A10 让人重新输入 IF；
- A6 让人重新选择多条模板做包络。

新系统如果有统一的：
- Procedure；
- Segment；
- Fix；
- ProtectionArea；
- TurnConstraint；
- Obstacle；
- NavigationTolerance；

这些“重新拾取”大部分可以转化为对象间自动引用。

因此逆向旧软件时必须把“规范上必需的人为判断”和“仅因为旧软件架构简单而存在的人为拾取”分开记录。
